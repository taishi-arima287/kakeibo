# code-check: フォーマット → lint → テスト

CLAUDE.md の作業ルール「完了報告の前に pytest / ruff check / ruff format が通ることを確認する」を、毎回同じ手順で実行するためのスキル。

## 方針

- **自動修正ツールで直せるものだけ直す**。`ruff format` と `ruff check --fix` が変更するものは機械的で意味を変えないので任せてよい
- **テスト失敗や手動修正が必要な lint 違反は直さず報告する**。テストが落ちたとき、テストの期待値とコードのどちらが正しいのかは設計判断なので、ユーザーに委ねる
- `--unsafe-fixes` は使わない。挙動が変わる可能性がある修正だから

## 手順

プロジェクトルートで次の順に実行する。整形でコードが変わったあとで lint とテストを走らせれば、最後に通った状態がそのまま最終形になる。途中で失敗しても、全体の状況を報告できるよう最後まで実行する。

1. **整形**: `uv run ruff format .`
2. **lint (自動修正つき)**: `uv run ruff check --fix .`
   - `--fix` で import の並び替えなどが入った場合に備え、もう一度 `uv run ruff format .` を実行する（変更がなければ何も起きない）
3. **テスト**: `uv run pytest`
4. **変更の確認**: 1〜2 で書き換わったファイルを把握するため `git diff --stat` を見る。ただし作業前から未コミットの変更がある場合は、どれがツールによる変更かを区別できないので、各コマンドの出力（`N files reformatted`、`Fixed N errors` など）を根拠にする

## 報告フォーマット

次の形で日本語で報告する。全部通った場合は表と一言だけでよい。

```
| チェック     | 結果 | 備考                          |
|--------------|------|-------------------------------|
| ruff format  | ✅   | 2 files reformatted           |
| ruff check   | ❌   | 1 件自動修正、残り 1 件        |
| pytest       | ❌   | 24 passed, 1 failed           |
```

失敗がある場合は表の下に、残っている問題ごとに次を書く:

- **場所**: `ファイル:行` の形で
- **内容**: ruff のルールコード（例: `B008`）とメッセージ、またはテスト名と assertion の要点
- **原因の見立てと修正案**: どう直せそうかを短く。複数の選択肢があれば比較する。ただし実際の修正はしない

自動修正したファイルがあれば、何を直したか（整形 / import 並び替え など）も一行添える。
